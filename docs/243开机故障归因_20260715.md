# 243 开机故障归因报告 (2026-07-15)

> **事件**: 243 医院机房产品实例在院内断电后"进不去系统", 搬回后复现多种开机异常。
> **结果**: 定位 5 个相互叠加的独立根因, 全部修复并持久化; 定型开机基线 = 上电 → BIOS 自检 ~45s → 系统启动 ~12s → 屏幕出 `gnome26 login:` 并保持可见。
> **读者**: 运维接手人 / 复制部署人 / 未来遇到"又进不去了"的人。修复操作速查在 `deployment_243_gnome.md` 「开机疑难」章节, 本文回答"为什么"。

---

## 一、一句话归因

**没有任何一块硬件坏了。** 五个软件/配置层面的坑叠在一起, 再被"屏幕看着卡住 → 强制断电"的误判循环放大成连环故障:

```
医院断电 ──→ /data 脏盘 ──→ 开机全盘 fsck 20分钟(静默)
                                    │
              "看着像死机" ←────────┘
                    │
              强制断电 ──→ 打断 fsck, 下次开机重头再来 (死循环①)
                    │
              反复冷启动 ──→ X99 冷启动根盘偶发未就绪 ──→ kernel panic (故障②)
                    │
       就算侥幸启动成功 ──→ 空网口死等 2 分钟(静默) (故障③)
                    │
       就算全部走完 ──→ 没装桌面, graphical.target 无人接管 (故障④)
                    │
       且第 15 秒起 ──→ nvidia 驱动杀死文本控制台, login: 画在虚空 (故障⑤)
                    │
              屏幕永远"停在某一行" ──→ 回到"看着像死机" (死循环②)
```

⑤ 是最隐蔽也最关键的一个: **它让"系统其实好了"和"系统真的卡死"在屏幕上看起来一模一样**, 是所有误判的温床。

## 二、五个根因逐一归因

### 根因① /data 脏盘触发开机全盘 fsck — "卡 20 分钟"

- **症状**: 开机停在最后一行日志 (snapd.seeded / e2scrub / Mounting /data...) 20+ 分钟不动。
- **机理**: `/data` (1.1T 机械盘, SQL Server 数据) 的 ext4 周期性检查本来就是关的 (`Maximum mount count: -1`, `Check interval: 0`), 正常开机秒过。**唯一触发全盘检查的条件是脏标志**——断电/强制重启导致未干净卸载。1.1T + 2900 万块的全盘 fsck 就是 15-25 分钟, 且 systemd 跑它时**控制台无任何进度输出**。
- **为什么初始化时期从没见过**: 那时每次都干净关机, 盘永远 clean。这是**断电引入的回归**, 不是配置本来就坏。
- **修复**: fstab `/data` 行改 `defaults,nofail,x-systemd.device-timeout=15s 0 0` — pass=0 开机永不 fsck 该盘; 脏了也只在挂载时回放 journal (秒级)。需要深度检查时人工 `umount /data && fsck.ext4 -y /dev/sdb1`。
- **证据**: 手动 `mount /data` 秒成功且数据完好; `tune2fs -l` 显示周期检查全关; 修复后开机 fsck 单元只剩 1G 的 EFI 分区。

### 根因② X99 冷启动根盘未就绪 → kernel panic — "error -6"

- **症状**: `VFS: Cannot open root device UUID=c1836d77... error -6` → `Kernel panic: Unable to mount root fs`。间歇性: journalctl 记录多次 0-44 秒即崩的启动, 与正常启动交替。
- **机理**: 华南 X99-F8D 老主板冷启动时 SATA 控制器初始化偏慢, initramfs 到挂根盘那一刻盘偶尔还没枚举出来; 默认行为是**立即 panic** 而不是等待。反复冷断电显著放大出现概率。
- **排除项**: 根盘本身健康 (Intel 企业级 SSD, SMART PASSED, 坏道/CRC 全 0, 磨损仅 1%); SATA 链路成功启动时 6.0 Gbps 干净无 reset。**不是盘坏, 不是线松导致数据错**。
- **修复**: 内核参数加 `rootwait` — 根盘没出现就等, 出现了再挂载, 从机制上消灭这类 panic。
- **证据**: `journalctl --list-boots` 的短命启动记录; 加参后多次重启无复发。

### 根因③ 空网口死等 — "静默卡 2 分钟"

- **症状**: 日志停在 `Finished snapd.seeded...` 后约 2 分钟无输出, 然后才继续。
- **机理**: 机器双网口只插一根线 (enp7s0 常年 NO-CARRIER), `systemd-networkd-wait-online` 默认等**所有**网口 online, 空网口永远不会 online → 每次开机白等到 2 分钟超时, 服务标 failed。它 gate 了 network-online.target → docker → multi-user, 期间控制台不刷新。
- **修复**: `systemctl mask systemd-networkd-wait-online.service`。本机服务全绑 127.0.0.1/0.0.0.0, 无任何单元真正需要"开机即等外网就绪"。
- **证据**: `systemd-analyze blame` 该服务 2min81ms 一骑绝尘; mask 后 userspace 启动 2min4s → 9.2s。

### 根因④ graphical.target 但没装桌面 — "走完了也没登录框"

- **症状**: 启动实际已完成 (SSH 通、业务在线), 屏幕却停在日志末行, 无图形登录框。
- **机理**: 系统默认目标是 `graphical.target`, 但机器上**没有安装任何桌面/显示管理器** (无 gnome-shell / gdm3 / lightdm, 仅残留 xserver-xorg-core 底层库)。graphical.target "到达"了, 却没有组件去画登录界面; 文本 getty 又只在 tty 上, 不主动清屏重绘。
- **排除项**: 卖家猜测的 "nouveau 抢 GPU 导致 X 起不来" 不成立——nouveau 0 模块未加载, 且根本没有 X 可起。
- **修复**: `systemctl set-default multi-user.target`, 名实相符地做无头服务器。本机产品形态 = 医生用其它电脑浏览器访问 8090, 本机桌面无用户场景; 且装桌面会与 llama.cpp 抢 2080Ti 显存, 属反向操作。

### 根因⑤ nvidia_drm 杀死文本控制台 — "第 15 秒后屏幕永远定格" ★ 最关键

- **症状**: 开机前 15 秒日志正常显示, nvidia 驱动加载完成的瞬间屏幕定格; 此后按回车、Ctrl+Alt+F1/2/3 屏幕均无变化, 看起来与死机无异——但 SSH/业务完全正常。
- **机理** (Linux 启动显示权三段交接):
  1. UEFI 固件画面 → 2. 内核 `simpledrm` 沿用固件 framebuffer 画启动日志 → 3. 原生 GPU 驱动注册 DRM 设备时, 内核**无条件驱逐** simpledrm (同一显存孔径不能双主)。
  契约是: 驱逐者应提供替代控制台 (fbdev)。**nvidia 570 闭源驱动在本机双 2080Ti 上违约**——驱逐了 simpledrm 却不建任何 framebuffer, 内核只能把控制台挂到 **dummy device (画在虚空的假控制台)**:
  ```
  [ 2.18s] Console: switching to colour frame buffer device 160x50   ← simpledrm 上岗
  [15.17s] Console: switching to colour dummy device 80x25           ← 驱逐后无接替, 挂 dummy
  ```
  从此 getty/login 的一切输出写进虚空; VT 切换在内核里是成功的, 只是渲染无处可去。**这就是"系统好了"与"系统死了"在屏幕上无法区分的原因, 也是整场误判循环的温床。**
- **正规修法为何无效**: 内核参数 `nvidia-drm.modeset=1 nvidia-drm.fbdev=1` 已确认生效 (`/sys/module/.../modeset: Y, fbdev: Y`), 驱动依然不注册 fb (`/proc/fb` 空)。闭源驱动内部行为, 无法进一步干预; 双卡 vgaarb 还存在 boot VGA 抢占 (82:00.0 被 84:00.0 覆盖) 的浑水。
- **决定性事实**: `lsmod` 显示 `nvidia_drm used_by: 0` — **本机没有任何组件使用它**。nvidia 四模块分两条独立业务线: 计算线 `nvidia + nvidia_uvm` (CUDA/llama 用) 与显示线 `nvidia_modeset + nvidia_drm` (X/Wayland 用)。无头机上显示线是纯死重, nvidia_drm 唯一的"作用"就是每次开机杀控制台。
- **修复**: 彻底禁止 nvidia_drm 加载 → 驱逐永不发生 → simpledrm 从第 2 秒服务到永远:
  ```
  /etc/modprobe.d/disable-nvidia-drm.conf:
      blacklist nvidia_drm          # 拦 alias 自动加载
      install nvidia_drm /bin/false # 拦显式 modprobe
  sudo update-initramfs -u          # nvidia 模块在 initramfs 里, 不重建拦不住
  ```
  同时撤回 grub 里两个无效的 nvidia 参数, cmdline 只留 `rootwait`。
- **影响面评估**: CUDA 完全不受影响 (实测重启后双卡各载 ~20G 跑 llama 正常); 代价 = 本机永久无图形能力, 与产品形态一致。还原路径: 删 conf → `update-initramfs -u` → 恢复 graphical.target → 另装 gdm3/桌面。
- **附带结论**: 卖家此前也遇到"进不去图形界面", 归因为 nouveau 冲突——方向反了, 真凶是 nvidia 闭源驱动自己 (nouveau 从未加载)。

## 三、误判循环复盘 (流程教训)

本次真正造成损失放大的不是任何单一故障, 而是**人机界面的误判循环**:

| 误判 | 事实 | 教训 |
|---|---|---|
| "屏幕停住 = 死机" | fsck/网络等待均为静默, nvidia 杀控制台后连登录框都不可见 | 停住先 ping/SSH, 通了就不是死机 |
| "强制断电能重来" | 每次断电: 打断 fsck 重头再来 + /data 更脏 + 多一次冷启动 panic 抽奖 | **绝不硬断电** — `sudo reboot` / `sudo shutdown` |
| "卡在 Mounting /data = 盘坏了" | 盘 SMART 全健康, 是全盘 fsck 在静默跑 | 卡住先看卡在哪一行、查盘用 SMART 而不是猜 |
| "换显示器/HDMI 试试" | 前 15 秒日志能显示 = 显示链路必然是通的 | 显示问题先看 dmesg Console 切换记录 |
| "nouveau 抢 GPU" (卖家) | nouveau 0 模块; 真凶是 nvidia_drm 驱逐 simpledrm 后违约 | lsmod 一条命令即可证伪, 不要沿用二手归因 |

## 四、修复后基线与验证

```
上电 → BIOS 自检 ~45s (X99 正常) → 系统启动 ~12s → 屏幕出 gnome26 login: 并保持
     → docker/sqlserver/web(8090) 自启即用 → llama 加载 ~8 分钟后 30000 就绪
```

验证命令 (SSH 进去一眼全绿):

```bash
grep -o '/data ext4.*' /etc/fstab                      # nofail,...timeout=15s 0 0
cat /proc/cmdline | grep -o rootwait                    # rootwait
systemctl is-enabled systemd-networkd-wait-online       # masked
systemctl get-default                                   # multi-user.target
lsmod | grep -c '^nvidia_drm'                           # 0
cat /proc/fb                                            # 0 simpledrmdrmfb
systemd-analyze                                         # userspace ~9-12s
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8090/   # 200
```

已连续 3 次受控重启全绿 (2026-07-15)。

## 主线一: 药品精准度 38.7% 短板, 很可能是三个工程缺陷的叠加, 而非模型能力问题

三个独立机制, 恰好都砸在药品规则上:

### 1a. 2000 字符尾截断, 恰好吃掉判定指征所需的 ground-truth 诊断 (高危)

`runner.py:36` 把所有工具结果按 2000 **字符**硬截断后才喂给 LLM. 而 `drug_audit_lookup.py:346-379` 的 bulk 输出把命中药列表放前面、`【患者病案首页诊断 ground truth】` 块附在**最后**——工具自己写着"判定指征请优先用此". 命中药一多, 被截掉的恰好是判"有无适应症"的唯一硬证据. 模型看不到诊断, 就只能按 KB 限制条文倾向判 V. **RD20/R007 假阳性集中, 这是最合理的机制解释.**

同样模式: `search_notes.py:225-235` 把 `[否认段]/[选项框]` 反向语义告警 append 在末尾, 截掉后模型可能把"否认胸痛"当阳性指征.

**修法**: 工具返回分两段——"必留头部" (ground truth / 告警) + "可截明细", 截断只砍明细段; `_TRUNCATE` 提进 `llm.yaml` 可调. 改完立刻重跑 v2.1 药品批次对照.

### 1b. 28 条 M8 精选规则被 4 条 bulk 规则逻辑完全包含, 同药重复审计、重复计违规 (高危)

R007/RD01/RD02/RD03 四条 bulk 用 `drug_audit_lookup(rule_type=...)` 一次拉回患者**全部**命中药; 而 RD10-RD37 共 28 条单药精选规则的判定逻辑与 bulk 逐字相同 (对比 `R007.yaml` 与 `RD20.yaml`, 只差一句"重点确认 X"). 两者同优先级批跑: 患者用了艾普拉唑钠, R007 和 RD20 会**各判一次 V**——违规数被结构性放大, 且 32 条近同文本要并行维护.

**修法**: 精选 28 条下线 (或 status 降为 router 触发提示、不进 LLM), bulk 4 条独占药品审计.

### 1c. conf < 0.70 的 VIOLATION 没有任何闸拦 (高危, 已核验)

`verdict_gate.py:319` 的低置信闸只处理 `conf ∈ [0.70, 0.85)`. 模型输出 V conf=0.5、或 confidence 字段缺失 (`runner.py:342` 归 0.0) 时, **直通为 VIOLATION**, 还会产出"VIOLATION conf 0.00"这种自相矛盾的落库行.

**修法**: 一行语义修正——`conf < ceiling` 的 V 全部降 I (floor 以下更该降, 不是更不该降). 整个 gate 体系里性价比最高的补丁.

## 主线二: 防线结构是"预筛 → LLM 全程自由探索 → 补丁式后筛", 确定性判定应该下沉

现在的信任结构: LLM 从头到尾自由探索并裁决, gate 在落库前打补丁. 症状——`verdict_gate.py` 已长出 **8 道闸 + 7 个按 rule_id 的 allowlist 集合** (`verdict_gate.yaml`), 每消一类假阳性就加一道特判, 且已开始互相打架:

- **R205 (1 台手术按次多收全麻) 被⑥存在性闸误清**: R205 是计数问题, 闸只查 `has_anesthesia_service()` 存在性 (`verdict_gate.py:212-223`)——麻醉真实即 V→CLEAN, **真超收被 gate 亲手放走**. 这是 gate 制造的假阴性.
- **R156 同时挂在两个语义相反的闸里** (`verdict_gate.yaml:35-39,62-63`), 靠闸的执行顺序隐式协调, 易漏改.
- **②单次闸按"不同日期数"计次** (`fee_netting.py:108-111`): 同日重复收费塌缩成 1 → 放过.

### 结构性建议: 模板拆两层

以 M1 为例, "主项 A ∩ 附属 B 并存 + 文书无反证"里, **A∩B 并存是一条 SQL 就能确定性判出的事实**, 只有"文书无反证"真正需要 NLU. 把每个模板拆成:

```
确定性 precheck (Python)         →  产出结构化事实: A∩B 是否并存 / 次数 / 净额 / 日期
LLM 窄问题 (只喂事实+文书片段)    →  只回答 "文书是否构成反证"
```

四重收益: 假阳性从源头减少 (gate 的大半闸自然退役)、token 大减 (LLM 不再自由探索)、每条 V 的证据可机器复核 (现在 `Evidence` 是自由文本, `result.py:14-24`)、换院鲁棒性上升. M1/M2/M4 三模板 72 条规则都是这个形态. 不是重写——precheck 复用 `fee_netting` / `clinical_context` 已有确定性代码, 等于把 gate 从"事后否决"挪到"事前供证".

## 主线三: 换院即失效——系统对"本院字面名"的依赖是产品化的最大矛盾

正在接外部医院 (szx、data-hub 三链已通), 但三处核心逻辑仍钉死在**本院费用项目的字面名称**上. (注: 本轮 szx 诊断/手术源修复解决的是"喂给这套逻辑的数据是错的", 下面三条是"逻辑本身对换院不鲁棒", 两层问题独立存在.)

1. **Router 只剩一条腿, 且这条腿是字面名**. `applicable_*` 五段硬过滤是**整段死代码**——156 条规则 0 条填写, 且 `adapter.py:86-95` 把 gender/age 写死 None, 守卫恒假 (双重死). 预筛全压在 `trigger_keywords` 子串匹配上 (`router.py:304-317`), 而 keyword 是"PET-CT""口腔颌面软组织清创术"这类本院字面名. 换医院命名不同 → 60% 前缀兜底兜不住 → **静默漏检** (预筛的假阴性不进 LLM, 永远发现不了). 另有 17 条空 keyword 规则恒放行, 预筛对它们无效.
2. **费用分类是关键词启发式** (`search_fees.py:61-65`): "造影"同时在手术类和检查类词表里, dict 顺序决定归类; 未命中的药落"其他类", 药占比信号失真. **而 hub 契约里有国标 MXFYLB 类别码 + 医保项目编码** (`hub_source.py:88-89,101-102`)——数据里有官方答案, 工具在用关键词猜.
3. **Gate 的 exam 关键词靠 grep prompt_addon 文本** (`verdict_gate.py:132-146`), 模板措辞一变即静默回退 trigger_keywords.

**修法方向**: 规则触发与费用分类改为**医保编码/国标类别码优先, 名称兜底**. `field_alias.yaml` 别名层已存在但 router 没接. `applicable_*` 要么删掉 (最省), 要么真填数据并修 adapter——现状是最差的: 50 行不可达复杂度 + 一个大家以为存在的闸.

同一主线的模板维护隐患: **prompt-fit 重跑会静默覆盖人工手改**. `R151.yaml` 的 prompt_addon 里有 v1.5/v1.6 人工插入的 STEP 0 共识块, 但 `derived_from_template` 仍是 M2, `prompt_fit_runner.py:233-240` 无脏检查——谁重跑一次 prompt-fit, 专家共识就没了. 建议渲染时对比"上次渲染产物 hash", 不一致即拒绝覆盖.

## 医保专家视角: 四个信号盲区 (决定审计上限)

现有 10 个工具查得到"有没有", 查不到"多不多、先后、谁开的":

1. **单价 × 数量对 LLM 不可见 (最痛, 但数据已就绪)**. `search_fees.py:90-93` 只给 LLM 合计金额, `cnt` 仅用于退费符号. 超量收费、超标准收费、分解收费——飞检里占比最高的违规类型——都需要"数量 × 单价 vs 政策上限", 现在全盲. M4 (超标准收费) 12 条实际是在没有数量维度的情况下硬跑. **v2 更新**: hub 契约已带 `pric/cnt` 列 (`hub_source.py:94-95`), 内部 shi_fee 契约同样有——缺口只在工具层, fee 输出行加 `单价 × 数量` 两列即通.
2. **时序维度缺失**. 药品 KB 里大量"支付不超过 14 天""限二线 (一线无效后)"条文, 但没有任何工具能算用药天数、给药起点、药物先后顺序. 建议加 `patient_timeline(patient_id)` 工具: 按日聚合 用药/检查/手术/诊断 事件流, 一次调用给 LLM 全局时间轴——同时是 tool-call-merge 的最佳载体.
3. **科室/开单医师/执行人对 LLM 不可见 (数据已就绪)**. 分解收费、串换科室、虚构服务 (M5) 都需要"谁开的、谁执行的". **v2 更新**: hub 契约已带 开单/受单科室 + 开单/医嘱医师 (`hub_source.py:106-109`), 同样只差工具层暴露.
4. **检验/检查不对称**: lab 有跨天重复统计 (`search_lab_results.py:128-147`), exam 没有——"重复检查"类规则信号天然弱一档.

**方法论层**: 医保飞检 = 面上筛查 (跨患者大数据) + 点上核查 (病历审查). Javert 目前只有"点". 163 条里 39 条 P3 "单病历看不出", 正是缺"面". 路线图里的 `add-cross-patient-stats` 建议提为最高优先的新 change——已有 106 患者 ~5000 裁决基线, V 率 ≥50% 提报系统性违规的统计一旦跑通, 是向院方交付时说服力最强的一页.

## 性能与成本 (三个几乎零成本的现成优化)

1. **prompt cache: `tools_prompt` 排错了位置**. `prompt_assembler.py:130-134` 把静态的工具列表放在动态规则段**之后**, 公共前缀在规则段断裂. 挪到规则段之前, 公共前缀 = base+experience+hospital+tools——hit_rate 36%→60%+ 就是这一个移动 (对应路线图 `prompt-cache-optimize`).
2. **tool-call-merge 是 prompting 问题, 不用写复合工具**. `runner.py:224-254` 本来就逐个执行一条消息里的全部 `<tool_call>`——基础设施已支持一轮多调用, 只是 prompt 从没告诉模型可以并列发. base.txt 加一句"可在同一轮并列发出多个 tool_call" + 示例, 8-9 轮 → 2-3 轮 (对应路线图 `tool-call-merge`).
3. **`--concurrency` 是假并发**: `tool_executor.py:114-135` 的 `_cache_lock` 包住整个工具执行 (含 LabLoader 392MB 首建、pandas 全表切片), 所有线程被一把全局锁排队, 实际只有 LLM 调用真并行. 改 per-key compute-once 锁.

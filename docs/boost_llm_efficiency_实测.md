## 一、改动摘要 (三处结构性提速 + 信号解锁)

1. **prompt 静态段前置**: tools 段挪到规则个性化段之前, 公共前缀 = base+experience+hospital+tools
2. **一轮多 tool_call**: base.txt 明示可并列 (runner 本就支持), 8-9 轮 → 3-4 轮
3. **工具缓存 per-key 锁**: `--concurrency 5` 下不同工具调用不再排一把全局锁
4. **fee 行明细**: `单价×数量` + `[开单:科室/医师]` 追加进 `search_fees` 行输出

## 五、结论 (对照 proposal 预期)

| 指标 | proposal 预期 | 实测 |
|------|-------------|------|
| 每规则 LLM 轮数 | 8-9 → 2-3 | **8-9 → 3.3-4.6 ✅ 约减半** |
| prefix cache hit | 36% → 60%+ | 73% → 76-79% (36% 为过时口径; 增量 +3~6pp) |
| 批跑时长 | 约减半 | **+12% 吞吐** (0.216 → 0.242 规则/s), 未减半 |
| 裁决稳定 | 无 V 级意外差异 | 同代码 384 条 4 翻 (1.0%, 双向边界噪声) ✅ |

**批时长未减半的原因**: GPU token 吞吐是硬约束 — 一轮多调用省掉的是 API 往返次数与
逐轮尾部重预填, 不减少总 token 量; 且改前 prefix cache 已 ~73%, 逐轮重读本就便宜.
轮数减半的实际收益: 往返失败面减半 (超时/解析失败机会少一半)、串行/低并发场景
(现场 `jv-run` 单患者) 时延改善最大、tool budget 触顶率下降.
per-key 锁的收益在冷启动场景 (LabLoader 392MB 首建不再挡全部线程), 本次热缓存批测不可见.
fee 明细信号 (量价/开单科室/医师) 为 M4 超标准/分解/串换科室类规则解锁, 属能力项非速度项.

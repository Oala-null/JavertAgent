## 二、审计性能详解

### 2.1 每条规则审计耗时

```
一条规则 × 一位患者 = 一次独立审计

审计流程:
  组装 prompt → LLM 思考 → 调工具取数据 → LLM 再思考 → 输出裁决
  └─ 60~90 秒 ─┘
```

| 指标 | 数值 | 说明 |
|------|------|------|
| **平均耗时** | **65 秒/条** | 模板优化后的稳定水平 |
| 中位数 | 60 秒 | 50% 的规则在 1 分钟内完成 |
| 最快 | 30 秒 | 费用无命中 → 第 1 步即 CLEAN |
| 最慢 | 224 秒 | 含量化计算的 M4 超标准收费 (多轮验证) |
| P90 | 95 秒 | 90% 的规则在 1.5 分钟内完成 |

**耗时分布** (按模板):

| 模板 | 平均耗时 | 原因 |
|------|---------|------|
| M1 重复收费 | 70 秒 | 查 2 类费用 + 文书验证 |
| M2 过度检查 | 59 秒 | 查费用+诊断, prompt 收敛快 |
| M3 口腔串换 | 64 秒 | 科室检查第 1 步即可判定 |
| M4 超标准收费 | 92 秒 | 含诊疗目录量化计算, 工具调用多 |
| M5 虚构服务 | 82 秒 | 费用+文书交叉验证, 需多节文书 |
| M6 过度诊疗 | 71 秒 | 排除诊断列表匹配 |
| M7 串换收费 | 68 秒 | 费用项比对 |

### 2.2 工具调用模式

**每条规则平均发起 4-5 次工具调用**:

```
典型调用序列 (以 M1 重复收费为例):

  Turn 1: search_fees(keyword="全身断层")     ← 查主项费用
          返回 2 条匹配, 耗时 0.3s

  Turn 2: search_fees(keyword="图文报告")     ← 查附属费用
          返回 1 条匹配, 耗时 0.3s

  Turn 3: search_notes(keyword="PET-CT")     ← 查文书佐证
          返回 3 条段落, 耗时 0.5s

  Turn 4: 输出裁决 JSON                       ← 不需要更多证据

  合计: 3 次工具调用, 每次返回少量精准数据
```

**工具调用不是全量扫描**:
- 费用工具: 从该患者 117 条费用中按关键字筛出 ≤20 条
- 文书工具: 从 152 条文书中按关键字/科室筛出 ≤10 段
- 单次工具调用耗时: 0.2-0.5 秒 (本地 CSV 检索)
- LLM 思考耗时: 占总时间 95% 以上 (模型推理是主要瓶颈)

**工具缓存**:
- 同一患者的多条规则共享工具缓存 (同样的查询不重复执行)
- 缓存命中率: 35%-62% (规则间有大量重叠查询)
- 缓存效果: 工具调用总量减少 40%+

### 2.3 Router 预筛效率

**问题**: 111 条规则全跑 = 每位患者 ~2 小时，不可接受

**解决**: Router 在 LLM 介入前用规则过滤，2 秒内完成

```
原始: 111 条规则 × 1 患者 = 111 次 LLM 审计 (~2 小时)
      ↓ Router 三层过滤 (耗时 <2 秒)
结果: 35 条规则 × 1 患者 = 35 次 LLM 审计 (~38 分钟)

节省: 68% 的 LLM 调用被安全砍掉
```

| Router 过滤层 | 机制 | 砍掉比例 |
|--------------|------|---------|
| 属性过滤 | 科室/性别/年龄/诊断不匹配 | ~30% |
| 关键字匹配 | 费用+诊断中无触发词 | ~40% |
| 合计 | | **~68%** |

**准确性验证**: 50 位患者实测，被 Router 跳过的规则中 **0 条漏检** (所有真阳性 VIOLATION 均保留)。

### 2.4 单患者审计总耗时

| 场景 | 规则数 | 并发度 | 耗时 | 适用 |
|------|--------|--------|------|------|
| 全量 P0 (不用 Router) | 57 条 | 串行 | ~83 分钟 | 基准测试 |
| 全量 P0 (不用 Router) | 57 条 | 并发 5 | ~18 分钟 | 快速扫描 |
| Router + P0 | ~18 条 | 并发 5 | ~7 分钟 | **推荐模式** |
| Router + 全量 ready | ~35 条 | 并发 5 | ~12 分钟 | 全覆盖模式 |

**推荐配置: Router + 并发 5 = 每位患者 7-12 分钟**

## 四、并发与日审核量

### 4.1 实测单患者耗时 (50 人 · Router + 规则内并发 5)

**配置**: Router 预筛 + 每位患者内部 5 条规则并行审计 (concurrency=5)

| 分位 | 耗时 | 说明 |
|------|------|------|
| 最快 | **1.4 分钟** | 轻量患者 (~4 条规则命中), 费用少、科室简单 |
| P25 | **8.4 分钟** | 四分之一患者在 8 分钟内完成 |
| **中位数** | **10.6 分钟** | **典型患者** |
| **平均** | **10.7 分钟** | 50 患者整体均值 |
| P75 | **14.3 分钟** | 四分之三患者在 15 分钟内完成 |
| P90 | **17.7 分钟** | 仅 10% 重症/复杂患者超过 18 分钟 |
| 最慢 | **22.6 分钟** | 重症患者 (~60 条规则命中), 多科室交叉 |

### 4.2 患者复杂度分档

| 档位 | 占比 | 平均耗时 | 特征 |
|------|------|---------|------|
| 快速 (<5 分钟) | 16% (8 人) | 2.1 分钟 | 门诊转入、单科室、费用 <100 条 |
| 中等 (5-15 分钟) | **67% (33 人)** | 10.8 分钟 | **大部分住院患者** |
| 较重 (>15 分钟) | 16% (8 人) | 18.5 分钟 | 多科室会诊、大手术、费用 300+ 条 |

> 实测结论: **2/3 的患者在 5-15 分钟内审完**, 对应的是绝大多数普通住院病例。

### 4.3 并发层级说明

Javert 的并发分为两层:

```
层级 1: 规则内并发 (当前已实现)
  └─ 1 位患者 × 111 条规则 → Router 筛出 35 条 → 5 条同时跑
     效果: 单患者耗时从 ~40 分钟 压缩到 ~11 分钟 (3.6× 提速)

层级 2: 患者间并行 (需多卡 GPU 支撑)
  └─ 多位患者同时审计, 每位走独立 GPU 推理流水线
     效果: 吞吐量线性增长
```

**当前瓶颈**: 1 张 GPU (RTX 5880 Ada 48GB) 支撑**规则内并发 5** 是稳定上限。
超过 5 并发会导致 sglang 推理队列拥堵, 超时率上升。
患者间并行需要额外 GPU 卡。

## 五、性能瓶颈与优化空间

### 5.1 耗时分解

```
单条规则审计 65 秒 = ?

  LLM 推理 (GPU):     60 秒 (92%)  ← 主瓶颈
  工具调用 (本地 IO):   3 秒 (5%)
  prompt 组装 + 结果解析: 2 秒 (3%)
```

**LLM 推理是绝对瓶颈** — 工具查询和数据加载不到 5 秒。

### 5.2 已实施的优化

| 优化项 | 效果 | 说明 |
|--------|------|------|
| 模板化 prompt | -10% 耗时 | LLM 收敛更快, 减少探索性调用 |
| patient_id 自动注入 | -15% 工具调用 | 消除 LLM 首轮探索 "患者是谁" |
| 并发执行 | 3-5× 吞吐 | 多条规则并行审计 (GPU 利用率提升) |
| Router 预筛 | -68% LLM 调用 | 不相关规则不进 LLM |
| 工具缓存共享 | -40% 工具调用 | 同患者跨规则复用查询结果 |
| deadline 兜底 | 100% 有效裁决率 | 工具调用超限时强制收敛 |

### 5.3 后续可优化方向

| 方向 | 预期提速 | 说明 |
|------|---------|------|
| prompt cache 优化 | 1.3-1.5× | sglang 缓存命中率从 36% 提升到 60%+ |
| 复合工具 (audit_bundle) | 1.5-2× | 一次调用返回全量患者数据, 减少往返 |
| 更快模型 | 2-3× | 下一代模型或更小参数量 |

## Context

v2 当前先构造 v1 结果，再为全部 `run_ids` 重新读取 SQLite、解析 evidence/tool calls、扫描患者费用表并生成卡片；每次轮询都会从头执行。v3 又在 v2 卡片上逐项扫描费用行。现网大结果集因此单次 GET 超过调用方 30 秒超时，而且超时后的下一次 GET 会重复同一工作。审计 run 在一个 attempt 内不可变，适合按 `attempt_id + run_id + api_version` 增量复用。

## Goals / Non-Goals

**Goals:**

- 一个 attempt 内，每个 run 的 v2/v3 卡片最多完成一次昂贵投影。
- running 轮询只构建新完成的 run；终态重复轮询直接复用缓存。
- 同患者并发 GET 不产生缓存击穿，且返回内容与无缓存路径完全一致。
- 新 attempt 不读取旧 attempt 卡片；缓存有明确上限，不形成无界 PHI 内存增长。

**Non-Goals:**

- 不修改审计并发度、Router 规则数或 LLM 执行速度。
- 不改变 v1/v2/v3 字段、排序、命中语义或重提语义。
- 不新增 Redis、数据库表或第三方依赖。

## Decisions

1. **按卡片而非整包缓存。** 缓存键使用 `(api_version, projection_scope, run_id)`；正常任务的 scope 是 `attempt_id`，重启后的 SQLite 历史回放使用有序 run ID 集合的 SHA-256 摘要。这样 running 状态从 13 张增长到 29 张时只计算新增 16 张，历史回放也能在首次重建后复用；整包缓存只能加速完全相同的进度，不能解决现网增量轮询超时。

2. **缓存序列化前的独立 card 副本。** 写入和读取均深拷贝，避免 v3 追加收费字段时污染 v2 缓存，也避免清理展示副本修改共享对象。外部 JSON 契约保持不变。

3. **使用进程内有界 LRU。** 卡片由当前 Web 进程确定性生成，缓存无需持久化；重启后自然清空。LRU 设置固定最大卡片数，淘汰只影响性能，不影响正确性。相比把卡片永久挂到 `_2c_tasks`，有界 LRU 不会随患者数无限增长。

4. **每个投影 scope 单飞构建。** 同一 attempt 或历史快照的 v2/v3 构建共用弱引用惰性锁；锁只串行化结果投影，不持有全局 `_2c_lock`，不会阻塞审计进度更新。不同 scope 仍可并行，锁在无请求持有后自动释放。

5. **匿名性能日志。** v2/v3 出口日志追加 `cache_hits/cache_misses/build_ms`，不记录患者号、attempt/run id 或业务原文，用于部署后验证。

## Risks / Trade-offs

- [首次大批量查询仍需构建尚未缓存的卡片] → running 轮询逐批填充缓存；单飞避免重复构建，并通过大结果集测试验证每个 run 仅解析一次。
- [缓存对象包含业务结果] → 仅保存在服务进程内、有界 LRU、重启即清空；日志不输出缓存键或内容。
- [并发请求等待同一 attempt 锁] → 等待者随后直接命中缓存；不持有任务状态锁，也不影响其他患者。
- [v3 修改 v2 对象导致版本串扰] → 缓存边界统一深拷贝，并增加 v2/v3 隔离测试。

## Migration Plan

1. 本地执行直接 2C、Web 组合和完整回归，并严格校验 OpenSpec。
2. 备份 62 当前源码和 mode 0600 `.env`，仅覆盖审计路由文件。
3. 重启 `javert-web`，核对 systemd、HTTP、SQL/Hub 和关键环境实值。
4. 对现有大结果患者连续查询，验证首次/重复请求耗时、缓存日志和 JSON 结构。
5. 回滚时恢复备份的 `routes_audit.py` 并重启；无数据库回滚。

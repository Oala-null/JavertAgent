## Context

当前 Rule YAML 同时承载来源字段、运行状态、Router 触发条件、LLM 处理说明和确定性预检。完整字段适合机器执行，但不适合医保、临床和运营专家在同一张表中快速评审。国家 0325 清单、药品派生规则和本地专家扩展规则又具有不同来源，不能把当前 `question` 一律冒充为国家清单原文。

本 change 先交付一份无患者数据的协作工作簿，用于验证专家分级和意见收集方式，不改变运行时规则合同。

## Goals / Non-Goals

**Goals:**

- 让专家在主 Sheet 一眼看到原文、简明处理方式、三档分级、意见和当前状态。
- 让三档分级成为 Rule 的显式字段，并为当前全部规则提供可修改的首版值。
- 覆盖当前工作树全部 Rule YAML，并保留来源差异和技术字段追溯。
- 用下拉、冻结表头、筛选和条件颜色降低多人填写门槛。
- 对规则数、规则 ID、主表列数、三档字典、空等级初始值和来源文本做确定性 QA。

**Non-Goals:**

- 不从 Excel 自动回写 Rule YAML，不把 Excel 变成运行时 source of truth。
- 不新增登录、权限、审批发布或实时协作平台。
- 不修改 `priority`、`verdict`、Router、SQLite/SQL Server 或 2C 接口。

## Decisions

### 1. 只保留两个 Sheet

- `规则协作主表` 固定六列：规则编号、原始规则原文、我们的处理、处理等级、专家意见、状态。
- `技术明细` 保存来源类型、当前字段、模板、触发词、工具和预检等信息。

选择两张表而非把所有字段放在主表，是为了让专家无需横向浏览二十余列；技术人员仍能用规则编号追溯完整配置。

### 2. 分级先由系统给出首版，专家后续修订

Rule 新增 `handling_level`，只允许三档：

- `违规（阻断）`
- `可疑（警告）`
- `提醒（引导）`

“合规”属于患者运行结果，不进入规则静态分级。现有 `priority` 也不复用，因为它控制规则筛选和执行顺序。

首版采用简单、可解释的迁移口径：

- 无非空处理逻辑或固定进入现场核查的规则 → `提醒（引导）`。
- 已 ready 且违规类型属于重复收费、超标准收费、分解收费或串换项目，并且不是 review-only 预检 → `违规（阻断）`。
- 其余涉及临床指征、虚构举证、医保资格、药品条件或尚在 drafting 的规则 → `可疑（警告）`。

该口径只产生首版静态元数据，不改变患者运行时三态，也不新增自动分级器。后续专家直接修改具体 YAML 字段和协作表即可，不维护第二套映射配置。

### 3. 主表处理说明采用确定性摘要

优先取 `prompt_addon` 首个实质段落并压缩空白；没有处理说明时使用 notes 提示；仍为空则显示“尚未形成自动处理逻辑”。摘要限制长度，完整 `prompt_addon` 保存在技术明细中。采用确定性规则而非重新用模型改写，保证重复生成稳定且不引入临床含义漂移。

### 4. 原始文本与当前规则文本分离

- 对国家清单中存在的 `Rxxx`，主表优先展示 0325 来源行的“问题”原文。
- 对无 0325 行的 `RDxx` 和 `R317+` 专家扩展，主表展示当前规则问题，并在技术明细标记来源类型。
- 技术明细同时保留来源原文和当前 `question`，避免规范化标点或后续修订破坏追溯。

### 5. 输出只包含规则元数据

工作簿不得包含患者号、病历、收费明细、run/ownership 标识、凭据或环境连接信息。输出文件保存在本次交付目录中，并通过内容检查和所有 Sheet 的渲染检查后交付。

## Risks / Trade-offs

- [简明摘要可能遗漏处理边界] → 技术明细保留完整 prompt、预期信号和 notes，主表明确用于概览而非执行依据。
- [初始分级不是最终专家共识] → 工作簿标明“首版分级，可调整”，运行时仍以原 verdict 逻辑为准；专家确认后直接修改 YAML 字段。
- [专家误改原文字段] → 原文列采用只读视觉样式，处理等级和专家意见采用黄色输入样式；本期不做 Excel 自动回写。
- [静态 Excel 存在多人冲突] → 先用共享文件和版本历史试运行；出现权限、审批或冲突需求后再提内部平台 change。
- [来源集合并非原始 163 条的同一集合] → 技术明细显式记录国家清单、药品派生和专家扩展三类来源。
- [颜色被误解为患者裁决] → 顶部图例明确这是“规则处理等级”，不改变患者 `verdict`。

## Context

249基线为8645a2d，已叠加侧栏和DETAIL结算补丁。名单查询曾由用户确认3,054份有指标报告对应633个首页，这只是当时快照。旧批跑额外用出院小结就诊号筛LIS而返回0。院内无法由本机直接访问，发布必须离线、可回滚，且不得写中台表。

## Goals / Non-Goals

Goals：同一四表路径驱动全量候选、实际LIS读取、快照与页面；全部候选有明确处理状态；可后台执行及恢复；提供完整操作文件夹。

Non-Goals：不全局更换费用/文书/检查的就诊号，不修改DETAIL/STFSJ、不改规则和模型，不把候选唯一误认成住院归属已证实，不自动把633写成验收人数。

## Decisions

1. 所有TB_* SQL和内部列映射留在hub_source。候选完全复用原E条件，保留每个SYXH；不接小结、费用或时间筛选。运行时不固定人数，不使用TOP1500截断全量。
2. LIS报告使用MEDICAL_RECORD.JZLSH接REPORT，再以院区/BGDH/BGRQ接INDICATORS。费用与文书仍复用既有HospitalPatient，LIS不依赖其visit值。指标通过EXISTS医疗记录关联，防止文书/医疗记录重复行放大指标。
3. 候选与证据分开。报告需同院、同KH/KLX、正常医疗记录；首页和医疗记录的入出院日期一致，并能唯一定位首页。以日期粒度对齐不同来源的时间精度，独立于旧费用/小结60秒校验。多个日期候选可用一致且有效的BAH进一步消歧；BAH口径不同不单独排除日期已唯一的记录。报告键多就诊冲突、缺时间、多个首页或其他次住院进入待核查，不进入审计labs。
4. 仅更换LIS路径不能解决缺费用/文书等其他输入。全量批跑保留全名单，逐人记录成功、Router跳过、关联/原文缺失、化验待核查、失败；只有形成有效本次住院快照者才调用审计。不得以跳过或源数据问题冒充成功。
5. 保留16列化验CSV契约，归属统计单独写preflight，审计前验证来源版本、化验文件摘要及行数；待核查化验另存受控快照并在页面单独标注，审计不读取它。快照/日志只留院内0700/0600目录。
6. 原文API只加lab_linkage和待核查列表。前端区分“本次住院检验”与“待确认归属”；前后端缓存增加短TTL，错误不缓存。热更新重启已确认Web，保留侧栏修复。
7. 批跑冻结候选、标签和代码指纹，先写STARTED再执行单例，持原批跑/单例锁。后台只输出索引、计数与错误码；恢复只跳过已核实的完成状态，未确认的STARTED不自动重跑。临床数据错误逐人记录，连接/配置/审计写入失败中止并可恢复。
8. 安装复用上一版白名单、SHA、原配置、备份与回滚机制。目标是已安装DETAIL及侧栏版本；新文件允许before=null。保持部署基线不变，通过receipt识别增量。无Git/pip/网络下载要求，无SQL DDL。

## Risks / Trade-offs

- 日期相同但住院归属仍有歧义 → 全院同卡首页反查唯一性，不能唯一时待核查；不放宽为全部历史报告。
- 部分候选临床数据不足 → 留在全量处理报告中，不能承诺633个均产出审计结果。
- 修改归属规则后旧快照不再可信 → 新来源摘要门禁要求重新抽取，历史结果保留。
- 用户闭SSH或中途退出 → tmux和原子进度；开始过而无完成凭据的患者停止自动恢复。
- 安装遇上运行中任务/未知文件修改 → 停止安装；不强杀批跑或覆盖其他补丁。

## Migration Plan

上传文件夹/ZIP至249，校验→只读检查→等待任务空闲→备份安装并重启Web→少量同批验收→恢复同批处理全部候选。失败时按保存的BACKUP回滚新补丁，保留DETAIL和侧栏及历史审计记录。Windows仅中转，解压和执行在249；也支持上传已解压目录后校验内部SHA。

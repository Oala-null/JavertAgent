## Context

用户最终决定不合并 fp8（7572a00），保留 gnome-243 的 3da4d80 为基线。真实数据源是医院提供的 SQL Server；本机只能根据现场只读输出验证，不能声称已连通院内。已知部署坑包括：院区 AYY8BNRF 与测试 0001/0003 混存、OPERATION 拼写、三种编号不同、七月首页与八月费用批次不同、文书时间全为占位、SQL 端口 1533、CLI 环境不等于 Web 进程环境。

## Goals / Non-Goals

Goals：先稳定跑通单例，复用既有转换和审计逻辑，保留多例独立运行、tag、只读预检和回滚。
Non-Goals：不迁移数据库、不连142更新知识库、不合入fp8、不升级模型/依赖、不改规则ready状态、不改医院原始记录。

## Decisions

1. 配置增加显式 `hub_linkage_mode=legacy|shanghai` 与 `hub_hospital_code`；默认legacy保持旧接口，新模式要求院区且拒绝0001/0003测试代码。不开全局KH聚合。
2. 每次患者读取先解析唯一首页，再用院区+BAH找唯一小结，校验KH/KLX相同、真实入出院时间有效且相差不超过60秒（部署保护阈值，不是标准规定）；缺失或冲突报稳定错误码，不退回同名号码。校验院区+BAH首页唯一与院区+JZLSH小结、登记唯一，登记卡信息和入院时间也须一致。
3. 返回显式患者上下文，现有fetch函数接受可选上下文：费用/检验/检查/小结使用visit，BA诊断手术使用syxh，扩展文书使用bah；全部绑定院区参数。转换后所有内部ID仍以syxh为本次审计键，机构键使用真实院区而不是YYJC中文名称。
4. 复用共享bundle入口接入ETL/HubRawSource；历史函数无上下文时保留legacy行为。文书过滤空/横线，1900时间为空并记录计数警告；不伪造时间。费用使用真实标准类别映射，检测EXT连接扩行。
5. 本次聚焦单例：没有小结/费用/有效病历的候选显式失败并跳过，不生成可审计“空快照”。提供最多100个候选中的首个通过者，供院内shell接收，不把患者清单带出医院；新模式ETL拒绝--all和多ID，批量等现场单例验收后再推进，单患者并发1。
6. 打包基于已推送的HEAD，只包含运行时白名单（源码、规则、路由及依赖声明等），不打包env/数据/venv/模型。现场先验包并确认停Web/批跑，备份旧受控代码；发布脚本保护.env和configs/llm.yaml等现场配置，不动SQL/SQLite。回滚恢复受控代码，不回滚业务数据。现机指纹/依赖可用性/旧版特有启动方式须现场核验。

## Risks / Trade-offs

- 60秒阈值只涵盖已观察4秒偏差 → 不放大为时间近似自动找病人，仍要求唯一BAH与同卡；超阈值显式阻断。
- 部分检验检查可能不是就诊流水号 → 不使用KH全历次兜底，现场预检列出空源；不宣称该规则证据已齐全。
- 文书JLSJ不可用 → 保留缺失并警告，时序类规则仍可能证据不足，临床人员复核。
- gnome tip包含历史知识库提交，依赖与实机可能有差异 → 不新增依赖，部署前在现有.venv做import检查，不在线uv sync。
- 不确认停服务无法保证一致更新 → 安装命令要求显式停服务确认，原子单文件替换、备份清单、失败可回滚；不猜测systemd单位或杀全局Python。

## Migration Plan

本地测试与proposal严格校验 → 提交并推送gnome-243 → 用远端一致SHA打包/验包 → 经医院允许通道上传 → 实机核对版本、配置、依赖、空间和停服务 → 备份安装 → 单例预检/审计、工作台验收 → 20例。每步分别记录状态；院内未完成门禁保持未勾选。

## Context

参照 `4f2e7d5`，上次62发布 `fcf7628`。两者相同合成72主卡：旧版559527字节不压缩，luo gzip7544字节（重复合成文本，非真实比例）；A→B→A来源查询9对2。62当前索引包含 patient_id/rule_id/created_at/id；详情 SQL 通常几十毫秒，而旧费用锚点回放重复10次净额处理、侧栏冷读约3秒。

## Goals / Non-Goals

目标：补齐传输与重复查询优化；费用预处理同请求最多一次且输出不变。非目标：替换快分支、改变规则、建立索引、重算历史结果或修改患者数据。

## Decisions

- 使用项目已有 Starlette GZipMiddleware，minimum_size=1000；实际 SSE 回归为门禁。
- 已知来源标签30秒、有界4096项进程缓存（None也可能代表数据库异常，因此未知来源不跨请求缓存）；详情和 profile 选源共用，审核成功时清除；既有MAX(id)轮询签名变化也清除侧栏和来源缓存。侧栏60秒，只缓存摘要，仍在完成查询后开始计时。
- 惰性函数用标准库 functools.cache，在当前请求闭包内共享费用行。resolve_hits 的可选工厂参数兼容所有老调用者；单独调用纯函数也只在第一条收费证据需要时准备一次。请求结束释放，无跨患者/跨请求费用缓存。
- 复制 luo 的实用优化，不复制带患者标识的计时日志。现场测量只回传函数名、耗时和计数。

## Risks / Trade-offs

来源标签最多30秒、侧栏最多60秒陈旧；写入后的刷新不应改业务归属规则。单个新患者的首次概览计算仍有成本。SQL合并CTE的性能不能只凭注释认定，62慢病统计必须保留；本次先解决已实测的重复计算。

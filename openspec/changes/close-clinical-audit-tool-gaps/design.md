## Context

本次缺口位于同一条证据链的多个层面：TP 费用表已经保存 `MXXMDW` 和 `YZID`，但 `hub_source.fetch_fees()` 未映射；`TB_CIS_DRADVICE_DETAIL` 已存在，但 schema manifest、DataLoader 和工具层没有医嘱能力；OCR 医嘱、检验和检查报告常以 `TB_CIS_MEDICAL_DOCUMENT` 全文存在，而专用工具只查结构化表；仓库已有两版诊疗目录，但运行时无查询工具且生产制品不携带工作簿。结果是 Router 能看到部分项目名，LLM 却拿不到计价、医嘱和报告证据。

约束包括：142 的 `sh_yb_platform` 只读，不能迁移其 schema；TP OCR 历史原始数据不能删除或重写；生产只能部署已提交 HEAD；Git 内不能新增真实患者材料；新能力必须兼容旧 CSV 缺列和非 OCR 患者。

## Goals / Non-Goals

**Goals:**

- 在 Javert 读侧一次性补齐费用单位、医嘱、目录和 OCR 报告兜底。
- 让结构化证据优先，全文证据只在结构化数据缺失时保守兜底并标明来源强度。
- 用四条眼科扩展规则覆盖专家给出的五个问题，并保证 Router 召回。
- 不改历史结果；通过合成夹具和已发布 OCR 病例只读回放证明缺口关闭。

**Non-Goals:**

- 不在本期重做 OCR/Qwen 输出 schema，也不要求 2C 回填历史 `TB_CIS_DRADVICE_DETAIL`。
- 不从病历推断医院真实设备库存；无机构台账时只产生现场核查结论。
- 不把诊疗目录命中直接等同违规；目录只是证据，裁决仍需数量、时间、侧别或执行记录。
- 不把真实患者号、原文或运行标识写入 Git 测试夹具。

## Decisions

### 1. 医嘱复用现有 notes 契约，不新增第二套患者 DataLoader

`fetch_notes()` 在结构化医嘱表存在且有行时，把医嘱规范化为 `case_notes` 行，来源标记为 `data_hub_advice`；`search_orders` 从同一 DataLoader 读取，优先返回这些结构化行。没有结构化行的 OCR 历史病例从医嘱类文书提取关键词上下文，明确标记“非结构化候选”。

选择该方案是因为所有审计入口已经可靠地构造 `CsvLoader(notes, fees)`；新增 OrderLoader 会迫使 CLI、2C、Web、Hub cache 和 onboarding 同时扩接口。全文兜底不创造医嘱，只返回可定位的原文上下文。

### 2. 费用字段做可选追加，不破坏旧 CSV

`schema_manifest.fees` 在既有列尾增加 `unit` 和 `order_id`；Hub 映射读取 `MXXMDW`、`YZID`。`search_fees` 仅在列存在且非空时展示单位/医嘱关联，旧 CSV 行为保持不变。

### 3. 诊疗目录按日期选版本，工作簿直接作为只读运行时资产

新增 lazy `CatalogLoader`，加载仓库已有 2026-04-01 与 2026-07-01 工作簿并缓存。查询优先使用国家医保编码/医保编码/项目编码，名称查询只做保守规范化；传入服务日期时必须应用条目起止日期，不能用最新版覆盖历史就诊。部署制品显式携带两个工作簿，复用已安装的 pandas/xlrd，不生成第二份易漂移目录。

### 4. 检查和检验工具在结构化表为空时使用 notes 兜底

工具注册时把同一 DataLoader 传给 `search_examinations`、`search_lab_results`。专用 Loader 有记录时行为不变；无记录时按用户关键词或报告类标题搜索 notes，并返回“非结构化报告候选”，不能伪装成结构化结果。这样既关闭 OCR 历史缺口，也不改变普通患者的权威结构化路径。

### 5. 四条眼科扩展规则覆盖五个专家问题

- `R319`：结膜囊冲洗与眼压检查的计价单位、收费数量、独立医嘱/执行次数和侧别对账。
- `R320`：睑板腺治疗收费存在但无治疗执行记录；入院体征或医嘱只能证明指征/计划，不能证明执行。
- `R321`：床头心电图收费触发机构设备现场核查；使用 presence_review 预检在费用存在时确定性返回 INCONCLUSIVE、零 LLM，避免模型猜测机构能力。
- `R322`：A 型和 B 型超声同次共存时核对是否分别存在生物测量与后节检查指征；证据不足进入人工复核。

规则编号延续现有 `RNNN` schema，`R319-R322` 在 notes 中明确标记为专家扩展，不冒充 0325 原始条目。R319/R320 使用 presence precheck，R321 使用 presence_review，R322 使用中性 coexist_review precheck（只确认共存，不注入重复收费偏置），费用不存在时零 LLM。

### 6. 迁移仅追加，不回写历史患者数据

本期迁移是运行时读契约和部署资产迁移：老 CSV 缺列兼容、Hub 现查即可看到新字段、历史 OCR 文书由新工具即时兜底。历史 audit_runs 不批量重评；只有用户明确重跑的患者生成新结果。

## Risks / Trade-offs

- [全文医嘱可能把费用清单误当医嘱] → 结构化行优先；全文兜底限定医嘱类 section，并在输出中标注候选而非确定事实。
- [目录名称存在近似项或版本冲突] → 编码优先、日期过滤、返回候选而不自动裁决；歧义时规则输出 INCONCLUSIVE。
- [新规则增加 LLM 负载] → presence/coexist 预检和 Router 编码触发将无关患者确定性清掉。
- [工作簿增加部署物大小] → 两文件合计约 6 MB，可接受；不新增运行依赖。
- [设备规则无法确认医院资产] → 设计上明确只生成现场核查，不将缺数据当违规。
- [真实病例专家结论与目录版本冲突] → 保留费用原始单位、目录有效期和医嘱事实三套证据，禁止静默选择对裁决有利的一套。

## Migration Plan

1. 先发布可选费用字段、医嘱/目录/报告兜底工具和 Router 资产；所有新增行为均向后兼容。
2. 本地运行定向工具测试、Router 测试、Promise 门禁和全量测试；用语义化合成病例验证四条规则。
3. 对已发布 OCR 患者执行只读工具回放和规则 dry-run，确认四条均被召回且证据来源正确。
4. 提交并推送当前分支，从已提交 HEAD 构建受控部署物；安装到 62 的 `production-62`。
5. 重启后验证工作簿存在、工具注册、systemd、登录页、SQL/Hub、v3 submit/results；再决定是否对目标患者执行明确的规则重跑。
6. 回滚应用到上一受控 HEAD；不删除目录、不改 SQL schema、不回滚历史结果。
